# Task Flow

Task Flow 是显式触发的质量纪律。它不替代具体技术能力，也不强迫使用 skill；它只要求每个复杂任务经过四个关口：理解、选对能力、拿证据验证、卡住时止损。

只约束当前任务。任务完成后退出 Task Flow，等待用户下一次显式调用。

用户在任务中补充关键信息时（定位变更、角色增减、技术栈变化等），标记受影响的问题并重评估，不从头全问。

## 启动和退出

用户输入以下唯一触发词时启动：

```text
/taskflow
```

启动后先给出简短路线，不要写长篇仪式感文本：

```text
Task Flow 已激活
问题：...
需要的能力：...
能力计划：能力 -> 手段 -> 验证
验证方式：...
```

任务完成后自动退出。需要提前退出时，输入：

```text
/exit-taskflow
```

退出时只需输出结论和未完成项，不需要四问总结。

## 四问

```text
收到任务
  |
  |-- 1. 我真的理解了吗？
  |     |-- 读需求、代码、文档、错误输出或相关输入
  |     |-- 明确交付物、边界和成功标准
  |     |-- 用户没给验收标准时，先提出默认验收标准
  |     |-- 模糊就问，失败就先复现
  |     `-- 🔴 不通过：不准实现
  |
  |-- 2. 我用对能力了吗？
  |     |-- 判断需要诊断、实现、格式处理、审查、验证、资料查询还是浏览器检查
  |     |-- 写成“能力 -> 手段 -> 验证”的行动计划
  |     |-- 优先使用当前环境真实可用的工具和 skills
  |     |-- skill 只有在能明显提高正确率时才使用
  |     `-- 🔴 不通过：换能力、换工具，或说明没有合适 skill
  |
  |-- 3. 结果有证据证明对吗？
  |     |-- 按风险选择测试、构建、lint、curl、数据库检查、截图、渲染或 diff
  |     |-- 验证失败先诊断失败原因
  |     `-- 🔴 不通过：回到第 1 问或第 2 问
  |
  `-- 4. 卡住了怎么办？
        |-- 同一问题最多尝试三轮
        |-- 方向错了就回到理解
        |-- 工具或 skill 不可用就换路径
        `-- 🔴 三轮仍不过：诚实报告卡点、尝试和需要的帮助
```

## 1. 我真的理解了吗？

目的：防止在错误问题上高效执行。

必须做：

- 用一句话复述任务目标。
- 写出交付物：代码修改、bug 修复、审查意见、文档、文件成品、接口结果、分析结论等。
- 写出边界：哪些文件、模块、用户流程、数据、格式或外部约束不能破坏。
- 对已有系统，先读相关实现和调用链，不只搜文件名。
- 对 bug、失败、性能问题，优先复现或定位失败面。
- 对需求模糊处，只问最小必要问题。优先用「是/否」二选一问法，最多连续问 3 个问题就给出建议方案让用户确认。
- 如果用户没有给验收标准，先根据任务类型提出默认验收标准；只有默认标准会影响产品决策、数据安全、权限边界、对外接口契约或不可逆操作时，才停下来问用户。

通过条件：

- 能说清“要做什么、为什么做、涉及哪里、成功标准是什么”。
- 未给验收标准时，已经给出可执行的默认验收标准或明确提出阻塞问题。
- 知道下一步需要哪类能力。

🔴 不准做：

- 不读上下文直接改。
- 用用户描述替代复现。
- 把猜测当结论。

## 2. 我用对能力了吗？

目的：防止把 skill 当菜单，也防止加载了却没真用。

先拆能力需求，而不是先找 skill 名：

- 上下文发现：需要理解仓库、文档、领域约束或外部状态。
- 故障诊断：需要复现、缩小范围、验证根因。
- 实现修改：需要写代码、改配置、迁移数据或补测试。
- 格式处理：需要保持文档、PDF、表格、演示文稿、图片或二进制文件正确。
- 审查把关：需要找风险、回归、规范问题或遗漏测试。
- 交互验证：需要真实浏览器、截图、端到端流程或视觉检查。
- 最新资料：需要当前官方文档、版本、政策、价格、时间或外部状态。

从能力到计划：先确定任务需要哪类能力 → 对号入座 → 用下面四个问题筛工具或 skill → 落成计划。

选择工具或 skill 时按四个问题判断：

- 它是否覆盖当前任务必须的能力？
- 它是否提供普通工作流没有的流程、工具、资源或质量约束？
- 它的输出是否能在本轮验证？
- 它是否会引入不必要复杂度？

把能力选择落成行动计划：

```text
能力计划：
- 能力：...
  手段：...
  验证：...
```

Skill 合规确认：如果当前任务加载了任何 skill，在进入实现前必须逐条回答：

```text
Skill 加载清单：
  加载了哪些 skill？（名称 + 版本号）
  每个 skill 的核心约束或禁止项是什么？（摘录原文，不概括）
  当前实现方案是否满足所有核心约束？
  🔴 任一约束未满足 → 不通过，回到能力选择或调整方案
```

示例：

```text
能力计划：
- 能力：故障诊断
  手段：复现登录白屏，检查 console、路由守卫和用户信息接口
  验证：同一登录步骤不再白屏，console 无新增错误
- 能力：最小修复
  手段：只修改导致白屏的守卫逻辑
  验证：diff 只包含相关文件，前端构建通过
```

使用规则：

- 只使用当前环境真实可用的工具和 skills；不要发明名称。
- 按当前会话提供的 skill 使用方式加载和执行，不要写死某个不存在的调用接口。
- 如果选了 skill，必须按它的说明执行；不能只看一眼就说用了。
- 如果没有合适 skill，但任务仍可完成，直接用普通工作流完成，并说明没有额外 skill 必要。
- 如果缺少的 skill 或工具会实质阻塞正确性，向用户说明缺口和替代方案。
- Hermes 环境下，可用 skill-manager 安装 skill、用 multi-source-skill-search 搜索。

通过条件：

- 能说明使用了哪些能力、为什么需要、各自负责哪一段。
- 能把每个能力写成“能力 -> 手段 -> 验证”，并且验证能覆盖该能力的主要风险。
- 若使用 skill，能说明它要求做什么，以及哪些要求已经执行。

🔴 不准做：

- 因为名称相似就使用 skill。
- 为了显得专业而堆多个 skill。
- 缺 skill 时编造已安装或已执行。

## 3. 结果有证据证明对吗？

目的：把“完成”变成有证据的判断。

先按任务风险选择验证方式（高风险=数据/权限/支付/对外接口→必须全链路curl+数据库确认；中风险=逻辑变更→单元测试+构建+diff；低风险=文案/样式→肉眼检查）：

- 代码修改：测试、构建、lint、类型检查、关键 diff 检查。
- bug 修复：重新跑复现步骤，证明原问题不再出现。
- API 或后端：启动服务、curl 正常和异常路径、检查响应结构和状态码。
- 数据库：确认表、字段、写入结果、回滚或迁移影响。
- 前端：真实浏览器打开、关键交互、console、截图或端到端流程。
- 文件成品：渲染、打开、页面/公式/布局/图片检查。
- 代码审查：每个问题必须有文件路径、行号和影响说明。
- 规划或文档：检查是否覆盖用户目标、约束、验收标准和下一步。

需要项目专属检查时，读取 `references/quality-checks.md`，只选择与当前技术栈和改动风险相关的项。

通过条件：

- 验证证据必须直接引用工具输出（curl 响应、数据库查询结果、git diff、浏览器截图、终端输出）。不准仅写摘要（如"测试通过"、"200 OK"、"已完成"）。
- 每个已执行能力至少有一个对应验证证据，或明确说明为什么无法直接验证。
- 无法验证的部分已明确说明原因和残余风险。

🔴 不准做：

- 说"应该没问题"。
- 把"Done"、"Passed"、"200 OK"当验证证据；必须贴出实际响应内容。
- 只检查自己改的文件，不检查调用方或影响面。
- 验证失败后只修表面，不回到根因。

## 4. 卡住了怎么办？

目的：防止在错误方向上消耗时间。

出现以下信号，立即切换策略：

- 同一个错误或失败检查出现三次。
- 连续两次依赖猜测且都不成立。
- 使用的工具或 skill 与真实问题不匹配。
- 改动范围明显偏离用户最初目标。
- 外部工具、权限、网络或环境不可用。

### Fallback 表

| 触发条件 | 信号 | 一线修复 | 仍失败兜底 |
|----------|------|----------|-----------|
| 验证失败 | 同错误出现三次 | 回到第 1 问复现+读错误栈，定位根因 | 报告卡点、尝试过的方案、需要的帮助 |
| 方向偏离 | 改动范围远离用户目标 | 回到第 1 问重新读需求，确认交付物和边界 | 用 `/exit-taskflow` 退出，让用户重述需求 |
| 能力不匹配 | skill 用不上或结果不对 | 回到第 2 问换能力、换工具、或改用普通工作流 | 向用户说明缺口和替代方案 |
| 工具不可用 | 外部工具/权限/网络/环境不可用 | 报告不可用原因，给出可执行替代方案 | 阻塞性缺口需等用户提供方案 |
| 猜测不成立 | 连续两次猜测都错 | 停止猜测，回到第 1 问读代码/文档/错误输出 | 承认无法确定，请求用户指引 |

### 切换动作

- 理解错了：回到第 1 问，重新读需求、代码或证据。
- 能力选错了：回到第 2 问，换工具、换 skill，或改用普通工作流。
- 验证失败：回到第 1 问定位失败原因，不要继续扩大改动。
- 工具不可用：报告不可用原因，给出可执行替代方案。
- 🔴 三轮仍不过：停止尝试，报告卡在哪、试过什么、下一步需要什么。

🔴 不准做：

- 第四次重复同一方向。
- 编造验证结果。
- 不告诉用户就放弃。

## 输出纪律

执行中只在关口切换、验证失败、需要用户输入或完成时汇报。不要把四问展开成冗长模板。

正确：问1/2/3 正常通过时不输出任何内容，只记录结论。问1→问2 的切换不算「汇报事件」。错误：在每个关口中途汇报进展或复述已读内容。

最终回复包含：

```text
完成：...
能力/skill：...
验证：...
跳过的高相关检查：...
未验证/风险：...
```

保持用户使用的语言。用户用中文，就用中文；用户用英文，就用英文。
