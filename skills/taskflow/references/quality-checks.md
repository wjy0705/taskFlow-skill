# 质量检查参考 v0.3.1 (泛用场景指南)

在第 3 问“结果有证据证明对吗？”时，请根据当前任务的**实际场景（领域、技术栈、交付物类型）**按需查阅本文件，自行判断最合适的验证证据。

> [!WARNING]
> 本文件列出的均为【场景示例】。你必须根据实际情况灵活变通，绝对禁止生搬硬套（例如对纯文本任务要求跑 mvn test）。
> 唯一不变的铁律是：**不得伪造验证结果。如果在当前环境无法执行，必须执行环境受限降级，要求人类介入验证。**

## 通用证据 (跨领域强制适用)

- **Diff/补丁对比**：代码或文本实际改动符合预期，无乱码或无关截断。
- **真实的终端流**：`Code Block` 中包含构建、测试或脚本命令的真实标准输出流 (stdout)。
- **物理界面的反馈**：浏览器真实报错、DOM 节点存在截图、或 UI 显示正常的客观陈述。

## 场景检查启发库 (Heuristics)

### 场景 A: 任何后端 / API 服务 (不限语言)
代码规范：无被吞噬的空 `catch`；无硬编码敏感凭据；写操作不使用 GET 接口。
验证方式：
- 跑通对应的生态测试命令（`pytest`, `go test`, `mvn test`, `npm run test` 等）。
- 接口测试：必须提供包含 Header 的完整 `curl` 命令验证正/异常路径。

### 场景 B: 任何前端 / UI
代码规范：禁止无意义调试代码（`console.log`, `debugger`）残留；页面状态（Loading/Empty/Error）闭环。
验证方式：
- 跑通对应的打包/类型命令（`tsc`, `npm run build`）。
- 要求人类通过浏览器检查 Console 是否纯净。

### 场景 C: 数据库与存储
验证方式：
- 提供执行的 Schema / SQL 的执行反馈。
- 如果存在 MCP 连接工具，直接调取库表验证写入字段、索引是否正确落盘。

### 场景 D: 纯文本 / 架构设计 / 文档审核
验证方式：
- 文档交叉引用是否断裂？
- 架构图 (如 Mermaid) 是否能被成功渲染且无语法错误？
- 审查反馈必须附带具体的文件路径和行号，并说明改动建议，而不是泛泛而谈。

### 场景 E: 运维与基础设施
验证方式：
- 检查服务进程是否存在。
- 检查 `ping` 或端口监控的存活状态。
- 确认凭据配置未随日志明文外泄。
